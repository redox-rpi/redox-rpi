# Pi 400 and the Pi 4 family (BCM2711)

Status: **draft plan**, 2026-11-09, WBS 3.2 (owner for now: Architect).
Parent issue: [#299](https://github.com/redox-rpi/redox-rpi/issues/299).

The maintainer has ordered a Pi 400 and wants a first test version of
Redox on it, booting from the SD card and over the network. This page is
the plan for that test version: what the boot chain needs, what changes in
the kernel, which drivers are the minimum, and steps that can each be
tested on their own. Most of it applies to the Pi 4 Model B and the CM4 as
well, because they have the same SoC.

## State

- No Pi 400 or Pi 4 in the lab yet; nothing has run on real BCM2711
  hardware.
- **In QEMU `raspi4b` (2026-11-09):** the first test card boots to the
  serial login with 4 CPUs, and commands run. Branch
  [`pi400-bringup`](https://github.com/redox-rpi/redox-rpi/tree/pi400-bringup),
  experiment `pi400`. What it took:
  - kernel: the BCM2711 devicetree names the GIC-400 as its own interrupt
    parent, so the kernel never set it up (no serial interrupt, one CPU);
  - kernel: an external abort (a write to a device that is not there) was
    retried as a page fault forever and hung the system without a message;
  - base: `dwc2d`, `bcm2835-sdhostd` and `bcm2835-pwmaudiod` step aside on
    the BCM2711;
  - scripts: `make-sdcard.sh --local <img> --live --board pi4`,
    `scripts/qemu-raspi4b.sh` (`--card`, `--run`), `config/config-pi4.txt`.
- Test card for the first boot on the real Pi 400: see
  [First boot](#first-boot-on-the-pi-400) below.
- What already helps:
  - The upstream kernel finds its interrupt controller in the devicetree
    and already has a GICv2 driver for `arm,gic-400` (used on QEMU `virt`).
  - Our drivers take their registers from the devicetree and translate
    the bus addresses (`0x7e…`) through `ranges`, so a new base address
    is mostly no code change.
  - Our U-Boot (`v2026.10`, `rpi_arm64_defconfig`) is built for the Pi 3
    and the Pi 4. It drives GENET, the SD controller, and USB through
    PCIe and the VL805.
  - QEMU 10.2 on homenodellm has a `raspi4b` machine. It has no PCIe and
    no GENET, but it is enough for the serial console, the GIC, the timer
    and SMP.

## What is different from the Pi 3B+

| Part | Pi 3B+ (today) | Pi 400 | Effect for us |
|---|---|---|---|
| CPU | 4× Cortex-A53, 1.4 GHz | 4× Cortex-A72, 1.8 GHz | builds run as they are; `target-cpu` later |
| RAM | 1 GB | 4 GB | DMA limits (see Risks) |
| Interrupts | BCM2836 local controller + BCM2835 | GIC-400 (GICv2) | upstream driver; combine with our spin-table start |
| Timer | 19.2 MHz | 54 MHz | read `CNTFRQ`, never assume 19.2 MHz |
| Peripherals | ARM `0x3f000000` | ARM `0xfe000000`, bus still `0x7e000000` | devicetree `ranges`; nested buses (`scb`, `emmc2bus`) |
| UART | PL011 on GPIO 14/15 | PL011 used by Bluetooth by default | `dtoverlay=disable-bt` |
| SD card | sdhost (`bcm2835-sdhostd`) | EMMC2, an SDHCI 3.0 controller | port `bcm2835-sdhcid`, not sdhost |
| Ethernet | LAN7515 on USB (`dwc2d`) | GENET v5 in the SoC + BCM54213PE PHY | new driver |
| USB | DWC2 (`dwc2d`) | VL805 xHCI behind PCIe Gen2 x1; the keyboard is on it | PCIe host + `xhcid` |
| Graphics | VideoCore IV | VideoCore VI, 2× micro-HDMI | firmware framebuffer only for now |
| Boot ROM | `bootcode.bin` on SD or network | bootloader in an SPI EEPROM, network boot built in | no SD card needed for network boot |

`dwc2d`, `bcm2835-sdhostd`, `pwmaudiod` (no jack) and the open firmware
([open-firmware.md](open-firmware.md)) do not apply on the Pi 400.

## 1 Boot chain

```
EEPROM bootloader ── SD card or TFTP: start4.elf, fixup4.dat, config.txt,
                     bcm2711-rpi-400.dtb, overlays/disable-bt.dtbo, u-boot.bin
  → U-Boot (rpi_arm64) ── boot menu ([#243](https://github.com/redox-rpi/redox-rpi/issues/243)): this SD card / network redox/ / network stable/
     → bootloader-live.efi → RedoxFS into RAM → kernel
```

- **Keep U-Boot for the test version.** The EEPROM could start the kernel
  directly, but our only path into the kernel today goes through the UEFI
  bootloader (or `rpi-boot-stub` from [#15](https://github.com/redox-rpi/redox-rpi/issues/15), which has the Pi 3 mailbox
  address built in). U-Boot gives us for free: the boot menu, `netboot.scr`,
  HTTP download, the UEFI framebuffer, and the same `u-boot.bin` for both
  boards. Direct boot without U-Boot comes later ([#15](https://github.com/redox-rpi/redox-rpi/issues/15)).
- **Firmware files:** `start4.elf`, `fixup4.dat`, `bcm2711-rpi-400.dtb`
  (plus `bcm2711-rpi-4-b.dtb` and `bcm2711-rpi-cm4.dtb`, so the card fits
  the whole family) and `overlays/disable-bt.dtbo`. They can sit on the same
  FAT partition as the Pi 3 files: the Pi 3 reads `start.elf`, the Pi 4
  reads `start4.elf`.
- **`config.txt`:** today's [config/config.txt](../../config/config.txt)
  already has `arm_64bit=1`, `kernel=u-boot.bin`, `enable_uart=1` and
  `dtoverlay=disable-bt`, which the Pi 400 needs too. `dtoverlay=mmc` and
  `gpu_mem=16` are for the Pi 3 only and move into a `[pi3]` section; the
  Pi 400 gets its own:

  ```
  [pi3]
  dtoverlay=mmc         # SD card on the Arasan controller (Pi 3 only)
  gpu_mem=16

  [pi4]
  enable_gic=1          # default on the Pi 4; the firmware sets the GIC up for us
  total_mem=1024        # test version: stay below every DMA limit (see Risks)

  [all]
  ```

- **EEPROM:** update it to the current stable release once (Raspberry Pi
  Imager, "Misc utility images" → Bootloader → Pi 400 family). For network
  boot set `BOOT_ORDER=0xf21` (SD first, then network, then again) and
  `TFTP_PREFIX=0` (one directory per board serial number, as for the 3B+).
  `DHCP_TIMEOUT` and `TFTP_IP` only if our dnsmasq proxy does not answer.
- **Reused from the Pi 3B+ chain:** U-Boot and its boot menu ([#243](https://github.com/redox-rpi/redox-rpi/issues/243)),
  `netboot.scr`, the HTTP/TFTP server and the dnsmasq proxy on homenodellm
  ([netboot.md](../netboot.md)), `bootloader-live.efi`, `make-sdcard.sh`.
  New: `netboot.sh --board pi400` puts the Pi 4 firmware files into the
  board's serial directory; `make-sdcard.sh` copies them onto every card.

## 2 Kernel

| Item | Today | Pi 400 | Work |
|---|---|---|---|
| Interrupt controller | BCM2836 with our IPI patch (0001) | GIC-400 from the devicetree, upstream driver | check SGI (IPIs) and PPI routing on real hardware |
| SMP | spin-table (patch 0001) | firmware armstub: also spin-table at `0xd8`…`0xf0` | patch 0001 must not assume BCM2836 IPIs when the GIC is used |
| Timer | generic timer, 19.2 MHz | generic timer, 54 MHz, PPI through the GIC | check nothing hard-codes the frequency |
| UART | PL011 from the devicetree | PL011 at `0xfe201000` from the devicetree, 48 MHz clock | `disable-bt`; check the input patch 0007 |
| Reset | PM watchdog (patch 0002) | same block, `brcm,bcm2711-pm` | check the compatible list |
| Addresses | `ranges` of `/soc` | nested `ranges` (`/soc`, `/scb`, `/emmc2bus`) | test address translation through two levels |

Per-SoC tables ([#224](https://github.com/redox-rpi/redox-rpi/issues/224), `socdump`) get a `brcm,bcm2711` entry: 54 MHz
crystal, the new PLL and clock-manager values. No address may be fixed in
code: everything comes from the devicetree, which is also how the Zero 2 W
works today.

## 3 Minimum drivers for a test version

| Driver | What | Source | Size |
|---|---|---|---|
| Serial console | PL011 in the kernel and `getty` | exists | none |
| Display | framebuffer that U-Boot hands over (UEFI GOP), `vesad` + `fbcond` | exists, as on the 3B+ | small: check |
| SD card | EMMC2: SDHCI 3.0 at `mmc@7e340000`, 3.3 V, 50 MHz high speed, no UHS | port `bcm2835-sdhcid` (same SDHCI family) | medium |
| Network | GENET v5 with one RX and TX ring, BCM54213PE PHY over MDIO, MAC from the devicetree | new `bcmgenetd`; U-Boot's `bcmgenet.c` (about 700 lines) is the model | medium |
| USB, keyboard | Broadcom PCIe host (`brcm,bcm2711-pcie`: no ECAM, own index/data config access, own MSI), VL805 reset through the mailbox (`NOTIFY_XHCI_RESET`), `xhcid` on aarch64, `usbhubd`, `usbhidd` | new `pcid` backend, `rpi-firmwared` call, upstream `xhcid` | large |

A USB Ethernet adapter is no shortcut on the Pi 400: its USB ports are
behind the VL805 as well, so it needs the PCIe work first. GENET is less
work than PCIe and xHCI.

Network boot itself needs **no network driver in Redox**: U-Boot loads the
whole image into RAM, as on the 3B+ today. A login over the network
(`devshd`, pi-test) needs GENET.

### Step 0: what the maintainer does

1. **EEPROM:** with Raspberry Pi Imager, write "Bootloader (Pi 400 family),
   Network boot" to a spare card, boot the Pi 400 once from it (green
   screen), done. We then send the exact `BOOT_ORDER` and `TFTP_PREFIX`
   values; if Imager's default does not fit, a Raspberry Pi OS card with
   `rpi-eeprom-config --edit` does.
2. **Serial adapter** (3.3 V, never 5 V) on the GPIO header at the back:
   pin 6 GND, pin 8 (GPIO 14, TXD) to the adapter's RX, pin 10 (GPIO 15,
   RXD) to the adapter's TX. Leave the adapter's VCC unconnected. Plug it
   into homenodellm.
   - Please take an adapter with its own serial number (FTDI FT232R or
     CP2102), not a second Prolific. Today's 3B+ adapter is a Prolific
     with no serial number. With two of them, `ttyUSB0` and `ttyUSB1` can
     swap after a reboot, and the test agent would talk to the wrong Pi.
   - A udev rule with fixed names (`/dev/console-rpi3`,
     `/dev/console-pi400`) needs sudo on homenodellm. We send the rule.
3. **Ethernet** on the same switch as homenodellm.
4. **Power** through a second Shelly plug (below).
5. **HDMI:** micro-HDMI to HDMI cable from HDMI 0 to the NanoKVM, swapped
   with the 3B+ when needed, or a second capture device later.

## First boot on the Pi 400

A test card that should reach a login on the serial console. Draft: it
has only run in QEMU so far. About 20 minutes.

**You need:** a microSD card (any size from 1 GB), a USB serial adapter
for 3.3 V, the Pi 400 power supply (USB-C, 5 V / 3 A), and if possible a
monitor on the micro-HDMI port next to the SD slot (HDMI 0).

1. **Flash the card.** Image:
   `http://homenodellm:8080/sdcard/pi400-test-latest.img.xz` (today
   `pi400-test-v0.4.1-dev-47-g80718050+x54e8`, 21 MB). With Raspberry Pi
   Imager: "Use custom", then pick the `.img.xz`. With SwiftFlash:
   `sudo swiftflash redox:pi400-test`.
2. **Connect the serial adapter** to the 40-pin header at the back of the
   Pi 400, with the Pi switched off:

   | Pi 400 pin | Signal | Adapter |
   |---|---|---|
   | 6 | GND | GND |
   | 8 | GPIO 14, TXD | RX |
   | 10 | GPIO 15, RXD | TX |

   Do not connect the adapter's VCC or 5 V. The header is the Pi 4 header
   seen from behind, so photos of a Pi 4 show it mirrored: use a Pi 400
   pinout (for example pinout.xyz, "Raspberry Pi 400" view) to find pin 1.
3. **Open the serial console** at 115200 baud, 8N1, before switching on.
   On the Mac: `screen /dev/tty.usbserial-<name> 115200` (end with Ctrl-A
   K). On homenodellm the 3B+ adapter is `/dev/ttyUSB0`; leave that one
   alone and use the new device (`ttyUSB1`, check with `dmesg`).
4. **Put in the card and switch on** (plug in the power supply, or Fn+F10
   if the Pi 400 is off).

**What should appear:**

| After | Serial console | Screen |
|---|---|---|
| 1–3 s | nothing from the firmware (it is quiet by default) | rainbow square, then the firmware's text |
| 3–5 s | `U-Boot 2026.10 …`, then the boot menu: "1. This SD card", "2. Network: pi400/", "3. Network: stable/" | the same menu |
| +3 s | `redox-rpi: boot card pi400/` and `Redox OS Bootloader 1.0.0 on aarch64/UEFI` | the bootloader's mode menu |
| +5–20 s | `live: n/222 MiB`: the system is copied into RAM | |
| then | kernel messages, `CPU activation complete: 4 CPUs online`, the drivers, the banner `redox-rpi v0.4.1-dev-47-…` | console text, if the framebuffer works |
| 30–60 s | `redox login:` | |

Log in as `root` with the password `password`, then type:

```
uname -a
cat /etc/redox-rpi-release
ls /scheme
```

**What will not work yet (expected):** the Pi 400 keyboard in Redox (it
works in the U-Boot menu, but Redox has no PCIe and xHCI driver yet,
step d2), Ethernet in Redox (step e), the SD card as a disk in Redox
(step f; the system runs from RAM, so changes are lost at power-off),
sound, Wi-Fi. In the U-Boot menu the network entries need a netboot
directory on homenodellm that does not exist yet (step c).

**What to send back:**

- the whole serial log, from switching on to the login, plus the output
  of the three commands (copy from the terminal, or `screen -L` writes
  `screenlog.0`);
- a photo of the screen if the serial console stays empty;
- if nothing appears at all: take the card out, switch on without a card,
  and send a photo of the diagnostics screen (it shows the bootloader
  version and the board).

## Network boot on the Pi 400 (step c)

Boots the Pi 400 with **no SD card**: its EEPROM bootloader loads the
firmware and U-Boot over TFTP from homenodellm, and U-Boot loads Redox over
HTTP, as for the 3B+. Draft: QEMU has no Ethernet for the Pi 4, so this
has not run anywhere yet. Do the first boot from the SD card first; the
network boot is the second test.

**On homenodellm** (prepared, nothing to do): `/srv/tftp/pi400-fw/` holds
`start4.elf`, `fixup4.dat`, the BCM2711 devicetrees, `config.txt` and a
U-Boot that loads `pi400/netboot.scr`; `/srv/tftp/pi400/` holds the boot
menu, the live bootloader and the image
(`v0.4.1-dev-50-g5e3563af+x54e8`, experiment `pi400`, branch
`pi400-bringup`). Both are new directories; the 3B+ files and the
server's configuration are unchanged. Checked from homenodellm: TFTP
serves `pi400-fw/start4.elf` and `pi400/netboot.scr`, HTTP serves
`pi400/harddrive.img.gz`.

### EEPROM setting (once)

The bootloader settings live in the Pi 400's EEPROM. These four lines are
needed:

```
BOOT_ORDER=0xf21
TFTP_PREFIX=1
TFTP_PREFIX_STR=pi400-fw/
BOOT_UART=1
```

- `BOOT_ORDER=0xf21`: the SD card first, then the network, then again.
  With a card in the slot nothing changes; without a card it boots over
  the network.
- `TFTP_PREFIX=1` and `TFTP_PREFIX_STR=pi400-fw/`: fetch the files from
  `pi400-fw/` on the TFTP server, a fixed name instead of the board's
  serial number, which we do not know yet.
- `BOOT_UART=1`: the bootloader also prints its steps (DHCP, TFTP) on the
  serial console. Without it the serial console stays empty until U-Boot.

Keep the other lines that are already there.

**With Raspberry Pi OS** (the Pi's own tool; a spare card with Raspberry
Pi OS Lite, written with Raspberry Pi Imager):

1. Boot the Pi 400 from the Raspberry Pi OS card and log in.
2. `sudo rpi-eeprom-update -a` brings the bootloader to the current
   release; reboot if it says so.
3. `sudo -E rpi-eeprom-config --edit` opens the settings in an editor:
   change `BOOT_ORDER` and add the other three lines, save, quit.
4. `sudo reboot`: the new settings are written at this reboot.
5. Check with `rpi-eeprom-config`: it prints the four lines.

**With Raspberry Pi Imager only** ("Misc utility images", "Bootloader
(Pi 400 family)", "Network boot") you get network boot, but with the
serial-number directory instead of `pi400-fw/`. It works too: send us the
serial number (on the diagnostics screen without a card, or in the TFTP
log), and we put the files into that directory instead.

To undo: `rpi-eeprom-config --edit` again, or Imager's "SD card boot"
bootloader image.

### Booting

1. Take the SD card out (or leave it in and pick a network entry in the
   U-Boot menu, see below).
2. Ethernet cable to the same network as homenodellm, serial console
   open, power on.

**What should appear:**

| After | Serial console (with `BOOT_UART=1`) | Screen |
|---|---|---|
| 1–5 s | bootloader lines: `Boot mode: NETWORK`, DHCP, `TFTP … pi400-fw/start4.elf` | diagnostics screen with the same steps |
| +5 s | `U-Boot 2026.10 …`, `starting USB…`, DHCP over `ethernet@7d580000` | |
| +3 s | boot menu "1. Network: pi400/", "2. Network: stable/" (3 s), then `redox-rpi: boot net pi400/` | the menu |
| +5–10 s | the image (about 45 MB) over HTTP, then `Redox OS Bootloader`, `live: …` | |
| 30–60 s | kernel, `4 CPUs online`, `redox login:` | |

With the card in the slot, the card's own boot menu also offers
"Network: pi400/" (entry 2): choose it with the arrow keys on the Pi 400
keyboard (it works in U-Boot) or on the serial console.

**If it stops early:**

- The diagnostics screen or the serial console waits at DHCP or shows no
  TFTP: the network boot needs an answer from our DHCP proxy on
  homenodellm, which answers only Raspberry Pi MAC addresses starting with
  `b8:27:eb`, `dc:a6:32` or `e4:5f:01`. Newer boards may start with
  `2c:cf:67`, `d8:3a:dd` or `28:cd:c1` (the MAC is on the diagnostics
  screen). Then the proxy needs one more line, a change on homenodellm
  that waits for your OK. Until then, adding `TFTP_IP=192.168.178.120` to
  the EEPROM settings may already be enough.
- U-Boot starts but finds no network or no `netboot.scr`: send the log.

**What to send back:** the serial log from power on to the login (or to
where it stops), and a photo of the diagnostics screen if U-Boot never
appears.

## 5 Test setup without card swaps

- The EEPROM boots over the network when no card is in the slot (or the
  card fails), so the lab Pi 400 runs without a card. Firmware, U-Boot and
  image all come from homenodellm.
- With a card in, `BOOT_ORDER=0xf21` boots from it first, and the U-Boot
  menu still offers the network entries. The maintainer can use the same
  Pi with a card at the desk.
- Step f (SD driver) needs a card; it can stay in during network tests,
  because the U-Boot menu picks the network image by default.
- **Second Shelly plug: yes.** The Pi 400 has no reset pin we can reach
  and draws up to 3 A on 5 V, too much for a switched USB hub port. A
  second Shelly Plug S Gen3 for the Pi 400's power supply lets it be
  power-cycled after a hang without anyone at the desk. The rules of the
  first plug apply: switching needs the maintainer's OK
  ([pi-tests lab.md](https://github.com/redox-rpi/pi-tests/blob/main/lab.md)). A hang that only the plug can end
  is rarer once the serial reset works on the Pi 400 too.
- The test agent needs its board name in each queue row (`3b+` or
  `pi400`), its own serial device and its own Shelly. That is a small
  change in the agent and in the [pi-tests queue](https://github.com/redox-rpi/pi-tests/blob/main/queue.md);
  until then, Pi 400 rows run by hand.

## 6 Risks

| Risk | Effect | What we do |
|---|---|---|
| PCIe and xHCI on aarch64 | `xhcid` was written for x86, where DMA is cache-coherent; on the BCM2711 PCIe is not. No ECAM, own MSI controller | biggest step, last; try polling first, then INTx, then MSI; cache maintenance as in kernel patch 0050 |
| DMA address limits | legacy DMA reaches only the first 1 GB, PCIe inbound only 3 GB | `total_mem=1024` for the test version, lift it later per driver |
| Two serial adapters on homenodellm | device names swap, wrong Pi | adapter with serial number, udev names before the first Pi 400 row |
| Timer frequency | anything that assumes 19.2 MHz runs 2.8× wrong | grep before step a; read `CNTFRQ` |
| Drivers for the Pi 3 start on the Pi 400 | errors or hangs at boot | start a driver only if its devicetree node exists; leave them out of the Pi 400 build at first |
| EEPROM version | old bootloaders lack network boot fixes | update in step 0 |
| Upstream | no BCM2711 work upstream that we know of | keep board code in the devicetree path; offer GENET and the PCIe backend upstream later |

## 7 What the Pi 4 Model B and the CM4 get for free

Same SoC, same drivers. Different are the devicetree name
(`bcm2711-rpi-4-b.dtb`, `bcm2711-rpi-cm4.dtb`), RAM sizes up to 8 GB (the
DMA limits above matter more there), a VL805 with its own firmware chip on
newer Pi 4B boards (the reset message does no harm), and the audio jack,
CSI and DSI on the Pi 4B. A card or netboot directory for the Pi 400
should boot a Pi 4B unchanged. The CM4 with eMMC is the board for
automated firmware tests ([boards.md](boards.md#compute-modules)).
