([release-process.md](../release-process.md)). Tracking issue:

## Candidate rc1

The user asked for a v0.4 candidate on 2026-11-07. rc1 is current `main`
after the last `merge-next` set was merged (#204, #163, #137, #81, all
2026-11-07 ~21:19 UTC):

- commit [4804fe63](https://github.com/redox-rpi/redox-rpi/commit/4804fe63750cb6d438f31c829aba5b62fb0e97dd)

  --version v0.4.0-rc1` ([ci.md](../topics/ci.md#image-server)):

- netboot `keep/v0.4.0-rc1-netboot.img`, Zero 2 W `keep/v0.4.0-rc1-zero2w.img`.

Build ID, checksum and test results: [rc1 build](#rc1-build) below.

## Candidate rc2 (planned)

The user wants an **optional desktop** in the release image from rc2 on
(their words: "Nein, erst rc2"): Orbital and the COSMIC apps, started from
the console, as a **beta**, with its limits in the notes. Graphics prepares
it as a PR with its own Pi test and tells the build agent when it is
merged. rc2 is then built from that `main` like rc1; the automated rows
run again, and the visit adds a desktop check (start it from the console,
mouse, keyboard, the two COSMIC apps, back to the console).

## rc1 build

Built from 4804fe63 as **`v0.4.0-dev-738-g4804fe63+x12cb`**,
`--release v0.4.0-rc1 --experiment timesync`, in `~/redox-rpi-rel`
(`logs/v040-rc1-build.sh`, then `logs/v040-rc1-resume.sh`):

- SD card `redox-rpi-v0.4.0-rc1.img.xz`, published with
  `publish-sdcard.sh`, SHA-256
  `25b1030b80239e0a5ac87c16165eee66ff09bc81ff681280410c23d5b6d457f8`;
  `/.uuid` has id `redox-rpi`, version `v0.4.0-rc1`, commit `4804fe63750c`;
- netboot `keep/v0.4.0-rc1-netboot.img`, Zero 2 W `keep/v0.4.0-rc1-zero2w.img`
  (with their manifests in `keep/`).

Since #244, `make-sdcard.sh --local` needs `boot-local.scr` from
`scripts/netboot.sh`, so the SD card's `boot.scr` is the **U-Boot boot
menu** (this SD card, network `redox/`, network `stable/` from
192.168.178.120). For people outside the test network only the first entry
works; the visit checks that the card boots on its own with no key
pressed and no cable (test 6). The build wrote it with
`scripts/netboot.sh --server 192.168.178.120 --dir redox --tftp-dir build/tftp`
in the clone, not on the TFTP server.

The netboot build after the SD build stopped at the drift check:
`base: source differs from its commit plus patches`. Cause: base `0083`
(IPv4 multicast) applies only with fuzz since #81 put `0041` before it; the
cookbook's `patch` accepts that (fresh source, as in the SD build and the
nightly), `git apply` in the drift check does not. The fuzzy result is
right (checked in `netstack/src/scheme/netcfg/mod.rs`), so the netboot and
Zero 2 W images were built from a fresh base source too, the same state as
the SD build. The refresh of 0083 is
[PR #254](https://github.com/redox-rpi/redox-rpi/pull/254) (context lines
only, same source); rc2 builds with it.

Test 10 (download over HTTP, `sha256sum -c`, `xz -t`): **pass**.
QEMU (netboot, `--data`, `logs/v040-rc1-qemu.sh`): login after 35 s, all six
`pi-test.py` checks pass, 0 of 300 starts failed, banner `redox-rpi
v0.4.0-rc1`, no `pcid`/`rtcd` line, no `audiod` error;
`patches/experiments/pwm-audio/qemu-check.sh`: 15 of 15.

Test 15 (`scripts/relibc-tests.sh --experiment timesync` on 4804fe63, build
`v0.4.0-dev-738-g4804fe63+x36c5`): **pass**. `sys_socket/unixrecv`,
`unixrecvfrom` and `unixnonblock` pass; 319 tests, 18 failed (17 known),
5 on the list now pass (`stdio/mutex`, `getpeername`, `getsockopt`,
`recv`, `recvfrom`). The one new failure is `pthread/exit`, killed with
SIGKILL: #108, as in v0.3.0-rc4. Its fix is still the experiment
`self-exit-status`, so #108 stays a known issue although the issue is
closed.

Queue: **#285** (tests 1–5, 11, 13, 14, 16, 18, 20, Pi test agent) and
**#286** (the visit with the user: 6–9, 17, 19, 21). Test 12 is the next nightly run of a commit with the same
