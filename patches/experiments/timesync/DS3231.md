# timesync with a DS3231 real-time clock

Issue [#39](https://github.com/redox-rpi/redox-rpi/issues/39), branch
`ds3231` (on top of `i2c`), planned for v0.8.0. Needs the experiments
`gpio`, `i2c` and `timesync`:

```bash
scripts/build-image.sh --experiment gpio --experiment i2c --experiment timesync
```

- **At start** `timesync` reads the clock at `/scheme/i2c/1/68` (seven
  BCD registers from 0x00). It uses the time if the oscillator-stop flag
  (bit 7 of register 0x0f) is clear and all fields are valid BCD in range;
  then the newest of the RTC, the build time and the saved time wins.
  Otherwise it logs `not using the RTC: …` and goes on without it.
- **After each NTP answer** it writes the time back (24-hour mode) and
  clears the flag; the first time it logs `timesync: RTC set`.
- **No clock:** without `/scheme/i2c` or a device at 0x68 it skips the RTC
  without a message.
- `timesync -n` also prints the RTC's time.

## QEMU

QEMU has a DS1338 (the same time registers) on bus 1; its register 0x0f is
RAM and reads 00, so the DS3231 path works unchanged. Network-boot image
`v0.3.0-dev-149-gdf0730a+xb1c4`, `--device ds1338,bus=i2c-bus.1,address=0x68`,
2026-10-29:

| Run | Result |
|---|---|
| RTC, no network | `timesync: RTC 2026-10-29 11:09:56 UTC` (`-n`), then at boot `clock set to 2026-10-29 11:10:22 UTC from the RTC` |
| RTC and network, flag set by hand (`i2c set 68 f 80`) | `not using the RTC: its oscillator stopped (battery?)`, the build time instead, then `clock set … from pool.ntp.org`, `RTC set`; register 0x0f reads `00` again |
| No RTC, network | no RTC message, the time from `pool.ntp.org` as before |

In QEMU the network-boot image has no data partition, and `60_data`
blocks the boot for about 1.5 minutes before it gives up, so
`65_timesync` starts late there. On the Pi the partition mounts at once.

Not tested on a real Pi yet: needs a person to wire a DS3231 module (see
the [i2c README](../i2c/README.md#test-on-the-pi)).
